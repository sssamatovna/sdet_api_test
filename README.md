# Автотесты для API

---
## 📝 Описание
Репозиторий содержит автоматизированные API-тесты, написанные на Python 3.10 с использованием современных библиотек.
Тесты покрывают все основные точки доступа API приложения, согласно выданному техническому заданию.
В проект включены только позитивные кейсы, как указано в требованиях.

## 🚀 Технологии 
- Python 3.10+
- Pytest
- Requests
- Pydantic
- Allure Report
- pytest-xdist
- python-dotenv

## ⚙️ Установка и запуск

1.  **Клонируйте репозиторий:**
    ```bash
    git clone https://github.com/sssamatovna/sdet_api_test.git
    cd sdet_api_test
    ```

2.  **Создайте и активируйте виртуальное окружение:**
    ```bash
    # Для Windows
    python -m venv venv
    .\venv\Scripts\activate

    # Для macOS / Linux
    python3 -m venv venv
    source venv/bin/activate
    ```

3.  **Установите зависимости:**
    ```bash
    pip install -r requirements.txt
    ```

4.  **Настройте переменные окружения:**
    Скопируйте файл `.env.example` в новый файл с именем `.env` и при необходимости измените значение `API_HOST`.
    ```bash
    # Для Windows
    copy .env.example .env

    # Для macOS / Linux
    cp .env.example .env
    ```
    
##  ▶️ Запуск тестов

### Простой запуск

Выполняет все тесты в одном потоке.
```bash
pytest
```

### Параллельный запуск

Запускает тесты в несколько потоков.
```bash
pytest -n auto
```

### Запуск с генерацией Allure-отчета

1.  **Выполните тесты и соберите результаты:**
    ```bash
    pytest --alluredir=allure-results -n auto
    ```

2.  **Сгенерируйте и откройте HTML-отчет:**
    (Требуется установленный [Allure Commandline](https://docs.qameta.io/allure/#_installing_a_commandline))
    ```bash
    allure serve allure-results

## ⚙️ CI/CD

Проект настроен для автоматического запуска тестов с помощью GitHub Actions. 
Пайплайн запускается при каждом `push` в ветки `master`, а также при создании `Pull Request` в `master`.

## ✅ Позитивный тест-кейс №1

---
ID: ТС001
Название: Создание и последующее получение сущности

Шаги:
1. Отправить POST-запрос на /create с валидным телом.  
2. Сохранить id созданной сущности.  
3. Отправить GET-запрос на /get/{id} с полученным id.
4. Отправить GET-запрос на /getAll

Ожидаемый результат:
1. POST-запрос возвращает статус-код 200 и id > 0. 
2. GET-запрос возвращает статус-код 200 и тело ответа, полностью соответствующее отправленным данным.
3. GET-запрос (/getAll) возвращает статус-код 200 и список, содержащий созданную сущность.
---

## ✅ Позитивный тест-кейс №2
ID: ТС002
Название: Получение списка всех сущностей

Шаги:
1. Отправить GET-запрос на /getALL  

Ожидаемый результат:

## ✅ Позитивный тест-кейс №3
ID: ТС003
Название: Обновление существующей сущности

Шаги:
1. Создать новую сущность(предусловие).  
2. Отправить PATCH-запрос на /patch/{id} с новыми данными.
3. Отправить GET-запрос на /get/{id} для проверки изменений.

Ожидаемый результат:
1. PATCH-запрос возвращает статус-код 204.
2. Последующий GET-запрос возвращает обновленные данные сущности.

---
## ✅ Позитивный тест-кейс №4
ID: ТС004
Название: Удаление существующей сущности

Шаги:
1. Создать новую сущность(предусловие).
2. Отправить DELETE-запрос на /delete/{id}
3. Отправить GET-запрос на /get/{id} для проверки удаления.
4. Отправить GET-запрос на /getAll.

Ожидаемый результат:
1. DELETE-запрос возвращает статус-код 204.
2. Последующий GET-запрос возвращает код ошибки клиента (например, 404 Not Found)
3. GET-запрос (/getAll) возвращает статус-код 200 и список, не содержащий удаленную сущность.

Обнаружен баг: GET после DELETE для ID 9 возвращает 500 вместо ожидаемого 404.

## ✅ Позитивный тест-кейс №5
ID: ТС005
Название: Фильтрация списка сущностей по параметру `verified=true`

Шаги:
1. Создать две сущности: одну с `verified=true`, другую с `verified=false`.
2. Отправить GET-запрос на `/getALL` с query- параметром  `?verified=true`.

Ожидаемый результат:
1. Запрос возвращает статус-код `200`.
2. Список `entity` в ответе содержит только сущности, у которых поле `verified` имеет значение `true`.
